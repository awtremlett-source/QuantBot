## The demo key works, and it cannot trade

The smoke test connected and read the account. It also mapped what the key is
allowed to do, and the answer matters:

| endpoint | result |
|---|---|
| `account/summary` | granted |
| `positions` | granted |
| `orders` | **403** |
| `metadata/instruments` | **403** |
| `metadata/exchanges` | **403** |

**A key that cannot even read orders cannot place one.** That is the read-only
proof, and it was obtained without ever pointing anything at an order endpoint.

Two costs, both recorded rather than worked around:

1. **T212's instrument list is unreadable**, so the recording list is *not*
   checked against what Trading 212 actually offers. Only the 10 tickers the live
   account holds are proven to exist there.
2. **Order history is unreadable**, so FACTS row g cannot be settled
   automatically.

If you want both closed, regenerate the practice key with the **instruments**
(and ideally **history**) permission ticked. `docs/t212/SETUP.md` explains it.

## The recorder

Built first in S3 because the data cannot be fetched later — minute bars come
only 8 days per request, measured, not assumed. **Every day this does not run is
a day the bot can never be tested on.**

It captures raw only; S3b's front door is the only thing that may put bars in the
store. What it refuses to get wrong:

- **A forming bar is not a bar.** The last row of a live request is still being
  built, and saving it would store a high that has not happened yet.
- **Never overwrite.** A bar that comes back with different numbers goes to
  quarantine; the original stands. Which is right is a human's question.
- **Pence are not pounds.** A 100× jump is a unit change, not a market move.
- **Clocks change on different dates.** Tested across the week when the UK has
  moved and the US has not (25 Oct vs 1 Nov 2026), when the gap is 4 hours, not 5.
- **A gap it cannot fill is written down as LOST**, never interpolated.

Throttling gets a patient retry with backoff, then an honest LOST. The freshness
meter goes red after 2 weekdays without a good capture, and was proven red on a
planted week-old manifest before being trusted.

## A design mistake found and fixed mid-run

The first 1-hour backfill was writing **one file per trading day per ticker** —
about 500 days × 119 names ≈ **59,000 tiny files**, mostly filesystem overhead,
and hours of work. It was stopped and hourly data is now partitioned **by month**
(~36 files per ticker). Minute and 5-minute data stay day-partitioned, because one
day of minute bars is a real file. The 1,382 day-files already written were
**moved aside, not deleted** (`data/raw/superseded-1h-dayfiles-2026-09-30/`), and
the manifest carries a note saying why.

## Scheduling

`QB2-Recorder` is registered **per-user, no admin needed**: Monday–Friday, hourly
for 14 hours from 07:00, which covers London (08:00–16:30) and the US
(14:30–21:00 UK). The **at-logon** trigger needs administrator rights and was not
forced. Catch-up makes it optional, but if you want it, run this once in an
**admin** terminal:

```
schtasks /create /tn "QB2-Recorder-Logon" /tr "C:\Users\mtrem\TRADING\qb2\tools\run_recorder.bat" /sc ONLOGON /f
```
