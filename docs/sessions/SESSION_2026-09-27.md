## What reading the documentation actually changed

The brief carried a mentor's reading of Trading 212's API. Checking it against
their own pages changed four things, and two of them changed the plan:

1. **There is no trailing-stop order type, and no amend endpoint at all** — only
   cancel. So the moving stop cannot live at the broker. It is run by our own
   code, which is the half of *"the stop needs to come from either Trading 212 or
   the algorithm"* that survives contact with the facts. A stop run by our code
   watches prices only while the machine is awake, so **real money now waits for
   the always-on PC**: S13 (move) comes before S14 (ISA), and the plan gate
   asserts that order.
2. **The API cannot price a share we do not already own.** `currentPrice` appears
   only inside a *position*, the instrument metadata carries no price and
   refreshes every ten minutes, and there is no quotes or market-data section at
   all. P14's pre-trade price check therefore cannot be "ask the broker first" for
   a new buy — S2b has to design around it honestly.
3. **The order endpoints are not idempotent**, in their own words: "Sending the
   same request multiple times may result in duplicate orders." Any future send
   must read pending orders first, which is now a premortem row.
4. **The believed live-versus-demo order-type split is not in the documentation.**
   All four order types are documented for the API with no environment caveat, and
   the limitations page lists no such split. Recorded as **CONTRADICTED**, with
   the honest qualifier that absence of a statement is not proof of absence — so
   it is "not established" rather than disproved, and gets re-checked before
   anything relies on stop orders.

The long-standing auth flag is closed: **Basic, base64 of `KEY:SECRET`**, exactly
as the mentor read it, confirmed in their quickstart.
