# 2026-10-02 — S3c: the recorder made visible, and the fault it was hiding

Written for the operator. What went wrong, what it cost, and what now stops it.

## The short version

The recorder was being **killed part-way through every run**, and nothing said so.
Each run tried to backfill 93 brand-new names as well as top up the 128 old ones,
took over an hour, and was terminated before it finished. Names near the end of the
list were simply never reached — which is why 93 names still had no data at all two
days after being added.

The hourly run now takes **about one minute** instead of over an hour, because it
only fetches what each name is actually missing, and asks for forty names at a time
instead of one.

## Why there was nothing to read

`run_recorder.bat` wrote everything into one shared log, `recorder.log`. On
2026-10-01 that file **did not exist anywhere on disk**, so when I went looking for
why runs were failing there was nothing at all to look at. It appeared the next day,
and its entire contents were:

```
^C
  ...three pandas warnings...
^C^C
```

`^C` means the process was **terminated**, not that it crashed. There was no summary
line, because no run ever reached the end to print one.

**Now:** every run writes its own file in `logs/recorder/`, named by the time it
started, with the start time, the finish time, the duration and the exit code. The
batch file creates the folder if it is missing, keeps 30 days, and — importantly —
passes the exit code back, so a broken run can no longer report success to Task
Scheduler. The folder is gitignored and is scanned for secrets like source code.

## The guard that was missing

On 2026-10-01 four names — GOOG, AXP, APH and ADI — were walked past and ended the
day with no data, **no LOST record and no error**. Nothing recorded that they had
even been tried.

Every run now keeps a ledger: *names attempted = saved + lost + quarantined +
skipped(with a reason)*. A name that lands in none of those categories fails the run
loudly. The first real run after the change reconciled exactly:

```
1m hourly: attempted 226 = saved 87 + lost 0 + skipped 139 + errors 0
```

## Two jobs, deliberately separated

| | what it does | how long |
|---|---|---|
| **hourly** | tops up 1-minute bars from each name's last saved bar, forty at a time | about a minute |
| **catch-up** | backfills names with no history, and tops up the 5m and 1h series | slow, once a day |

The catch-up runs on the **day's last scheduled trigger**. That detail matters: the
task repeats hourly for 14 hours from 07:00, so its final run starts at 20:00 — while
New York is still open until 21:00. A catch-up that waited for "both markets shut"
would never have run at all on this schedule.

## Three more faults found on the way

**The recorder was re-reading the whole manifest twice for every single name.** With
226 names that is 452 full parses of a 5 MB file per run, just to count what it had
quarantined. It now gets that answer back directly from the function that did the
work. This was a large part of the "over an hour".

**Tests were writing into live data.** The quarantine folder was worked out once when
the module loaded, so when a test redirected the data folder the quarantine path did
not follow — every test that quarantined a bar wrote its made-up rows into the real
quarantine folder. Three such files were found and **moved aside, not deleted**.

**The quarantine was crying wolf.** 315 files had piled up for "changed" bars. I
measured the actual differences: **0.018% to 0.063%** — the provider rounding its own
numbers, not a bar changing. Hundreds of false alarms a day would bury the one real
conflict. A bar now has to differ by more than 0.1% to be treated as a conflict;
smaller revisions are still counted, in one line each, and the original bar still
stands. The loud path is unchanged and still proven by its own test.

## Two recorders can no longer run at once

An hourly job on a laptop overlaps with itself sooner or later — a catch-up started
by hand, a missed trigger firing late, a run still going when the next hour comes
round. Two processes writing one file can leave it truncated, and a truncated bar
file is worse than a missing one because it still reads. There is now one lock. An
overlapping run stands down and exits **0**, because the scheduler overlapping is
healthy and reporting it as a crash would cry wolf in the one place anyone looks.

## Earnings dates — done, and London is not thin

| sleeve | coverage |
|---|---|
| US shares | **30/30** |
| UK shares | **10/10** |
| London ETFs | 10 marked **N/A** — a basket of shares does not report results |

1,654 rows stored, including **40 future announcements**. I expected London to be
patchy and it is not: SHEL.L alone has 50 recorded dates.

Every row carries a **knowable_time** — the moment we fetched it. A back-test may
only use rows it could honestly have known at the time it is pretending to be.
Without that, a strategy "avoids" an announcement using a date that had not been
published yet, and prints a profit nobody could have earned. Earnings dates move,
which is exactly why this matters.

The advisor's 171 names are **not** covered yet; the box scoped this to the bot's 50.

## The quote delay is finally being measured

It had been "UNMEASURED" through three attempts, always because the markets were shut
when someone remembered to look. The sampler now runs **first in every run**, before
any fetch, so a long run can never swallow it again.

There is also a meter that goes **red when a trading session finishes with no samples
at all** — the absence of a measurement now looks like a problem instead of looking
like nothing. It was proven red against the three real sessions that had none.

## The window is gone — and the missing log is explained

The operator reported a window titled `C:\Windows\System32\cmd.exe` appearing every
hour. I probed it rather than assuming: I temporarily pointed the task at a
one-line program that writes down its own working directory, ran it, and read the
answer:

```
TASK STARTED IN : C:\Windows\system32
```

That is the whole explanation for the missing log. Task Scheduler starts a task in
System32 when no **Start in** is set, so the old `data\raw\intraday\recorder.log`
resolved to `C:\Windows\System32\data\raw\intraday\recorder.log` — a folder that
does not exist and cannot be created there. The redirect failed silently and the
log never appeared anywhere.

**The fix, proven by a real `Start-ScheduledTask` run:**

- the task now runs **`pythonw.exe`** directly — absolute path, no console at all;
- **Start in** is set to the repository;
- every path the run writes to is absolute, built from the code's own location.

Proof it is windowless: the running process reports `MainWindowHandle = 0` with no
window title, and no `cmd.exe` has it as a parent. Its log opens with:

```
started in directory: C:\Users\mtrem\TRADING
python: C:\Users\mtrem\TRADING\.venv-qb2\Scripts\pythonw.exe
```

**Nothing waits for a keypress.** No `pause`, no `cmd /k`; the run exits with its
own code, and that code reaches Task Scheduler. If a run is ever killed — a closed
window, a sleeping laptop — its log simply has no `run finished` line, and
`unfinished_runs()` lists it. The next run catches up from each name's last bar.

**Windows settings changed:** only the task's **action** and **Start in**. The
settings the operator chose — `IgnoreNew`, the battery rules, `StartWhenAvailable`
— were read before and after and are untouched. No administrator rights, no stored
password (`RunLevel: Limited`, `LogonType: Interactive`).

## Real run durations

| run | mode | duration | exit |
|---|---|---|---|
| scheduled task, 19:20 | hourly | **2.6 min** | 0 |
| hand run, 19:25 | hourly | **1.6 min** | 0 |
| scheduled task, 20:03 | hourly + catch-up | 110 min | 1 |

Against a baseline of **over an hour** for an hourly run that never finished. The
110-minute run is the catch-up doing its job — it backfilled all 226 names — and it
ran on the day's last trigger with nothing behind it.

**It exited 1, and that was my mistake, now fixed.** The 45-minute alarm is meant to
catch an *hourly* run overrunning its own trigger; applying it to the deliberate
after-hours catch-up reported correct behaviour as a failure. An alarm that cries
wolf is worse than none. The hourly stage is now judged on its own time, and the
catch-up has a separate, generous bound meant to catch one still running the next
morning.

## The census

**5-minute bars: GREEN — 217 of 221 names pass (98.2%), against a 95% bar.**

| sleeve | passing |
|---|---|
| US shares | 98/98 — 100% |
| UK shares | 97/100 — 97.0% |
| London ETFs | 22/23 — 95.7% |

The four that do not: BNZL.L (no intraday data at all), DCC.L, ITRK.L and MIDD.L
(between 64% and 77% of the bars a full session would hold).

**One-minute bars tell a different story, and it is not a fault.** 167 of 221 pass
(75.6%): US names 100%, UK shares 55%. Thinly-traded London shares simply **do not
trade every minute** — a minute with no trade has no bar and never will. Judging
one-minute completeness against an assumption of continuous trading is the wrong
test for London, which is why the census is defined on five-minute bars, where a
window almost always contains a trade. I have reported both rather than only the
one that passes.

## Is S3 done? No — and here is exactly what is left

All five of S3's exit-gate items are green, and the earnings dates I flagged as
missing yesterday are now in. But the stage's own text asks for **prices, dividends,
currency rates and earnings dates**, and:

1. **Dividends are not ingested at all.** P3 judges total return in pounds; a
   strategy scored on price alone is scored on the wrong number.
2. **Earnings cover the bot's 50 names only**, not the advisor's 171.

So S3 stays open, and the plan now says so. The next box finishes it.

## Still true, and worth watching

A handful of bars saved before today's fix may be unfinished ones (the guard
removed only the last trailing bar). Roughly 23 such readings were seen. Because a
changed bar is quarantined and **the original stands**, those few bars will not
correct themselves — they are recorded here rather than silently left.
