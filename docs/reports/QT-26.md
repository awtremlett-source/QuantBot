### B3. The fix, at the front door only

**New module qb2/ingest/refetch.py** (79 lines; pure, called only by `daily.ingest`):
- `merge(fresh, stored, broken)`: works out what to store, row by row:
  - a stored **sane** row whose session the re-fetch sent **broken**, the session having **closed**, is
    **kept**;
  - every re-fetched sane row is stored;
  - if a stored sane close differs, **the newer wins** and it is listed as a correction with both
    figures.
  - For the pound/dollar rate (no exchange close; its newest row is a moving rate, QT-25 B) a changed
    close is taken but not named. Otherwise every top-up would "correct" today's rate.
- `say(...)`: writes manifest lines: "kept" (each session with its close) and "corrected" (count, plus up
  to the newest 50 changes, each with both figures).
- `set_aside(bad, path)`: **adds** the fetch's broken bars to the quarantine file, never rewriting what
  it holds. The same bar sent again is held once.

**daily.py** (243 → 250, its limit):
- `broken` = the closed sessions this fetch sent broken. A session not yet closed is never "broken and
  closed", so QT-25's refusal stays as it was.
- The stored file is merged before the sticky cross-bar quarantine (cross_bar.apply), so that check still
  sees every row written.
- `DailyOutcome` gains `kept` and `corrected`.
- One-in-one-out: the inline quarantine rewrite (4 lines) and the `copy()` + assign pair are gone.

**daily_step.py** (167 → 182): the marker records `kept` and `corrected`, and the "Daily store:" line

## Part D — why Windows ran the tasks at 06:11 Monday and refused the status push (read-only)

**What I could read:**
- **Task Scheduler's own history log is switched off** on this PC ("Microsoft-Windows-TaskScheduler/
  Operational": enabled = False, no records). So Windows kept no record of why it started each task.
- The **System** log and each task's settings, read and nothing changed:

| when (UTC = UK) | what the System log says |
|---|---|
| Sat 24 Oct 01:49 | PC goes to sleep (after Friday's runs) |
| Sat 24 Oct 18:50 → Sun 25 Oct 03:49 | awake, then sleeps |
| Sun 25 Oct 01:00 | clocks go back: the time zone moves to GMT |
| Sun 25 Oct 17:56 → Mon 26 Oct 05:17 | awake; at 05:17 a **restart** begins ("Kernel API", the kind an update asks for); back up 05:19 |
| Mon 26 Oct 05:23 | sleep |
| **Mon 26 Oct 06:06** | **wakes** (source "unknown"); the clock jumps from 05:23 to 06:06 (re-read from the hardware clock: normal after sleep) |
| Mon 26 Oct 06:11:11 | Task Scheduler starts QB2-Recorder (its last-run time); QB2-StatusPush refused (0x800710E0) |
| Mon 26 Oct 06:20 | Windows Update installs two apps (the updates behind the restart) |

**The tasks' settings** (schtasks /query /xml, read only):
- **QB2-Recorder:** 14 weekday triggers, 07:00–20:00 local time; **"run as soon as possible after a
  scheduled start is missed" ON**; "wake the computer to run" ON; one instance at a time.
- **QB2-StatusPush:** 14 weekday triggers, 08:50–21:50; **catch-up OFF**, wake OFF; one instance at a
  time; 10-minute time limit.

**In plain words.**
- Windows decided that a recorder start had been missed. This came after the update restart, the sleep
  and the clock change all in one night. The recorder is set to catch up, so it ran once, five minutes
  after the PC woke. That is the "one catch-up after a switch-on" we expect: inside the cap, and correct.
- It tried the status push in the same sweep. The push is **not** set to catch up, and Windows refused
  it with 0x800710E0. That code means "the request was refused". It is Windows declining to start the
  task, not our program failing: nothing ran and nothing was half-written.
- The 08:50 push went out normally and carried the page. **Nothing was lost.**
- Exactly why Windows counted a missed start can't be read, because the history log is off. No trigger
  fell between Fri 20:00 and Mon 07:00. The restart plus the clock change is the likely cause.

**Change needed: none.** Both behaviours are safe: one extra catch-up inside the cap, and one refused push
that the next push covers. PROPOSE 8 (optional, for diagnosis only) is to switch Windows' task-history
log on, so a surprise like this can be explained next time. It is a Windows setting, so it is yours to
change, not mine.
